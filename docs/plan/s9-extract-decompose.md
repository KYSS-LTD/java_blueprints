# S9. Выделение метода и декомпозиция монолита

**Часы:** H34–44 · **Треки:** A (engine), C (UI) · **Веха:** M5 · **Требования:** FR-17, FR-18

## Цель

Автоматически выделять ответственности из монолита (`Main.java` ≈1000 строк: парсинг, анализ, оптимизация, вывод) в отдельные классы (`Parser`, `Analyzer`, `Optimizer`, `Main`…) при необходимости и подтверждать поведение quality gate. Реализовать выделение метода как самостоятельную операцию и как шаг декомпозиции.

## Зависимости

S2 (семантика: эффекты, чистота), S5 (правки текста, `rename_symbol`), S6 (gate), S7 (метрики, клоны, MAINT-правила), S8.1 (инфраструктура кандидатов и gate).

## Критерии выхода (веха M5 — заморозка функциональности)

- [ ] Выделение метода: корректные параметры, возврат, `throws`; результат компилируется; gate зелёный; клоны заменяются вызовом.
- [ ] Декомпозиция `demo-orders`: ≥ 3 класса, `javac` проходит, все сценарии зелёные (A6), `Main.java` уменьшился минимум вдвое.
- [ ] Повторный запуск с теми же настройками даёт идентичный результат.
- [ ] План можно править вручную до применения; предупреждения о перекрёстных зависимостях показываются.
- [ ] На сложных случаях декомпозиция не ломает проект: либо применяется корректно, либо отказывает с причиной.
- [ ] Все возможности из [01](../01-requirements.md) реализованы: после M5 новые функции не добавляются.
