# 10. Качество и тестирование самого инструмента

Это тесты **нашего** решения. Тесты поведения пользовательских Java-программ (сценарии, golden master) описаны в [07](07-behavior-verification.md); здесь — как мы убеждаемся, что сам инструмент работает.

## 1. Принципы

1. **Корпус примеров — главный актив.** Каждая функция проверяется на реальных Java-файлах из `samples/`.
2. **Инварианты вместо ручных проверок.** Round-trip, компилируемость результата, сохранение поведения проверяются автоматически на всём корпусе.
3. **Engine тестируется без HTTP и БД.** API-тесты — тонкий слой сверху.
4. **CI блокирует merge при красных тестах.** Скорость: быстрые тесты (< 60 с) на каждый push, медленные (JDK, E2E) — отдельной задачей.

## 2. Корпус `samples/`

| Каталог | Содержимое | Назначение |
|---|---|---|
| `samples/demo-orders/` | **Демо-монолит ≈1000 строк** (обработка заказов: ввод, валидация, анализ, оптимизируемые участки, вывод) + `scenarios/*.json` | Основной пример для демо и приёмки |
| `samples/analyzer-pairs/` | Пример со слайда 5 (`Analyzer.java` с вложенным циклом и `merge`) | Диагностика и OPT-01 |
| `samples/monoliths/` | 4–6 дополнительных монолитов 600–1200 строк на разные темы (сейчас: текстовый анализ, инвентарь, парсер выражений, граф), как у организаторов: сгенерированы ИИ, проверены вручную | Проверка обобщаемости: разбор, анализ, декомпозиция |
| `samples/scope/<id>/` | Минимальные программы по строкам таблицы покрытия ([04 § 9](04-code-graph-model.md#9-покрытие-java-scope)), по одной на раздел/конструкцию, + сценарии | Матрица покрытия scope |
| `samples/optimizations/<OPT-NN>/` | `before/Main.java`, `after/Main.java` (эталон), `negative/Main.java` (предусловие не выполнено), сценарии | Тесты преобразований |
| `samples/defects/<RULE>/` | Пример срабатывания и «чистый» пример (нет срабатывания) | Тесты правил анализа |
| `samples/out-of-scope/` | Код с потоками, `java.time`, файловым вводом-выводом | Проверка, что инструмент не падает (деградация в блок «Код») |
| `samples/broken/` | Файлы с синтаксическими ошибками | Устойчивость разбора |

Формат примера, сценариев и правила корпуса — в [samples/README.md](../samples/README.md); проверка — `scripts/verify_corpus.py` (нужен JDK) и `backend/tests/unit/test_corpus_layout.py` (без JDK). Фикстуры scope описывает одна таблица `samples/scope/README.md`, а не отдельные README.

Требования к каждому примеру в корпусе: компилируется `javac`, детерминированный вывод, ≥ 3 сценария, README в одну строку — что демонстрирует. Корпус демо-монолитов пишется так, чтобы в нём **заведомо** присутствовали: вложенный цикл поиска, `contains` по `ArrayList` в цикле, конкатенация строк в цикле, `==` для строк, пустой `catch`, длинный метод, дублирование, god-class с четырьмя ролями.

## 3. Уровни тестов

### 3.1 Модульные (engine) — `pytest`

| Область | Что проверяется |
|---|---|
| `java/` | Разбор конструкций scope; диапазоны (в т. ч. кириллица, UTF-16 колонки); семантическая модель: типы, области видимости, разрешение вызовов, эффекты, чистота |
| `graph/` | Блок-схема на каждый вид оператора (snapshot); ID стабильны при вставке строк выше; рёбра: Да/Нет, `break/continue`, исключения |
| `edit/` | Каждая операция: текст «до» → «после» (golden), невалидные фрагменты, перенос блоков, переименование по областям видимости |
| `analysis/` | Big O: таблица «фрагмент → ожидаемая сложность» (≥ 60 случаев); правила: срабатывание и несрабатывание; метрики |
| `transform/` | OPT/FIX/CLEAN/REF: «до/после», негативные, идемпотентность |
| `runtime/` | Компиляция, диагностики, запуск, таймауты, лимиты вывода, кириллица, необработанное исключение |
| `verify/` | Нормализация, маски, сравнение, нестабильные сценарии, генератор (покрытие), бенчмарк (k) |

### 3.2 Инвариантные тесты на корпусе (`test_corpus_invariants.py`)

Для каждого файла `samples/**/*.java`, кроме `broken/` и `out-of-scope/`:

| Инвариант | Проверка |
|---|---|
| I1 Разбор | Без ошибок; все `main`-классы найдены |
| I2 Round-trip | `apply([])` и «тождественные» операции возвращают тот же текст |
| I3 Покрытие графа | Объединение диапазонов блоков покрывает все операторы всех методов |
| I4 Компиляция | `javac` проходит на исходнике |
| I5 Определённость | Два прогона каждого сценария дают идентичный нормализованный вывод |
| I6 Операции | Для каждого блока: `duplicate` → `delete` дублирует и возвращает исходный текст; `wrap(block)` → `unwrap` — то же |
| I7 Анализ детерминирован | Два запуска анализа дают одинаковый JSON |
| I8 Автоисправления сохраняют поведение | Каждое `OPT-*`/`CLEAN-*`/`REF-*`, предложенное для файла, проходит gate по сценариям |
| I9 Декомпозиция | На монолитах: `javac` + сценарии зелёные, результат детерминирован |

### 3.3 Матрица scope (`test_scope_matrix.py`)

Параметризованный тест по `samples/scope/*`: I1–I4, I6 + проверка наличия ожидаемых видов блоков в схеме (`expected_kinds.json`) + генерация сценариев даёт покрытие > 0.

### 3.4 API-тесты — `pytest` + `fastapi.testclient.TestClient` (на `httpx2`)

Каждый эндпоинт: успех, ошибки (404/409/422), форматы. Сквозной сценарий: создать проект → получить граф → операция → версия → запуск → тест → экспорт. База — временный SQLite.

### 3.5 Frontend

- **Vitest:** адаптер `FlowGraph → React Flow`, хранилища, хук SSE (с фейковым `EventSource`), валидаторы форм.
- **Playwright E2E:** путь демо (раздел 5) на собранном приложении (`docker compose` или dev-серверы).
- **Линт и типы:** `eslint`, `tsc --noEmit`.

### 3.6 Нагрузка и производительность

| Метрика | Бюджет | Как проверяем |
|---|---|---|
| Разбор + граф, 1000 строк | ≤ 300 мс | `pytest-benchmark` на `demo-orders` |
| Операция над графом | ≤ 500 мс | Тайминг в API-тесте |
| Анализ | ≤ 1 с | Тайминг |
| Компиляция `demo-orders` | ≤ 3 с (холодная) | Тайминг |
| Gate, 15 сценариев | ≤ 20 с | Тайминг на CI-машине |
| Холст, 150 узлов | интерактивно (INP < 200 мс) | Ручная проверка + Playwright trace |

## 4. Приёмочные критерии MVP (Definition of Done проекта)

| № | Критерий | Как проверяется |
|---|---|---|
| A1 | Все пункты FR-01…FR-21 выполнены | Чек-лист в [plan/README.md](plan/README.md#матрица-покрытия-тз) |
| A2 | Все строки таблицы scope ([04 § 9](04-code-graph-model.md#9-покрытие-java-scope)) зелёные в `test_scope_matrix` (обязательный и бонусный scope) | CI |
| A3 | Инварианты I1–I9 зелёные на всём корпусе | CI |
| A4 | Демо-монолит: полный путь (загрузка → граф → правка → код → запуск → gate зелёный) без ручных обходов | Playwright E2E |
| A5 | Автооптимизация демо-монолита снижает сложность и даёт измеренное ускорение ≥ 2× | Отчёт бенчмарка |
| A6 | Декомпозиция демо-монолита → ≥ 3 класса, gate зелёный | Тест I9 + E2E |
| A7 | Негативный контроль: внесённая ошибка ловится gate | E2E |
| A8 | `docker compose up` с чистого клона поднимает приложение; демо-проект открывается | Ручная проверка на чистой машине |
| A9 | Комплект сдачи полон ([12](12-demo-and-submission.md#3-чек-лист-сдачи)) | Чек-лист |

## 5. E2E-сценарии Playwright

| Тест | Шаги |
|---|---|
| `demo_full_path` | Главная → пример «demo-orders» → открыть метод → граф виден (≥ 10 узлов) → клик по узлу подсвечивает строки → изменить условие в инспекторе → код обновился → «Запуск» → вывод → «Запустить тесты» → «Все тесты пройдены» |
| `code_to_graph` | Изменить код в Monaco → через ≤ 2 с схема обновилась |
| `diagnostics` | Открыть «Проблемы» → есть находка PERF-01 → клик → выделен узел; «Рекомендации» → предпросмотр → «Применить» → gate зелёный → сложность уменьшилась |
| `optimize_all` | «Оптимизировать» → план → применить → отчёт «до/после» |
| `decompose` | Вкладка декомпозиции → план → перенести метод между классами → применить → файлы появились → gate зелёный |
| `negative_control` | Изменить `+` на `-` → «Запустить тесты» → красный diff |
| `undo_redo` | Операция → undo → код как до → redo |
| `export` | «Экспорт Java» → архив скачан; (в тесте) компилируется `javac` |

Реализация — `frontend/e2e/*.spec.ts`, запуск `cd frontend && pnpm e2e` при поднятом приложении (`E2E_BASE_URL`, по умолчанию `http://localhost:3000`; без загрузки браузеров — `E2E_CHANNEL=msedge` или `chrome`). Каждый тест создаёт свой проект из примера `demo-orders` через API и пишет JUnit в `reports/playwright-report.xml`. Компиляция экспорта `javac` проверяется в `scripts/bug_bash.py`.

## 6. CI (GitHub Actions)

```
jobs:
  backend:   uv sync → ruff → mypy(engine) → pytest -m "not jdk and not slow"
  backend-jdk: (setup-java 21) → pytest -m "jdk"   # runtime, corpus invariants
  frontend:  pnpm i → gen:api (diff check) → eslint → tsc → vitest → next build
  e2e:       docker compose up -d → playwright test   # по метке или на main
```

Отчёты тестов (JUnit XML) сохраняются как артефакты; итоговый прогон на `main` копируется в `reports/` при сдаче (комплект сдачи, п. 03).

## 7. Отладка и наблюдаемость

- Структурные логи (JSON) с `request_id`; уровень `INFO` по умолчанию, `DEBUG` — `JB_LOG_LEVEL`.
- Каждый запуск Java пишет `tmp/run-<id>/` (сохраняется при `JB_KEEP_RUNS=1`).
- Эндпоинт `/api/health` проверяет `javac -version` и запись в БД.
- Дамп состояния проекта (`GET /export/bundle`) достаточен для воспроизведения бага.

## 8. Известные риски качества

| Риск | Смягчение |
|---|---|
| Вывод типов в семантической модели неполный | Консервативность: при неопределённости — не применять автоисправление; `javac` в gate — последний рубеж |
| Генерация сценариев не достигает покрытия на нестандартном вводе | Предупреждение «доказательство слабое», ручные сценарии, импорт, отчёт о непокрытых узлах |
| Нестабильный вывод (время, хеши) | Двойной прогон при записи эталона + маски |
| Монолиты организаторов используют конструкции вне нашей таблицы | Блок «Код» как запасной путь; открытый вопрос №1; корпус монолитов расширяется |
| Рост времени gate на тяжёлых сценариях | Параллельные JVM, лимиты, кеш сборки, таймаут + отчёт |
