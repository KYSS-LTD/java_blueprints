# Java Blueprints — описание решения

Кейс AXENIX «Визуальная среда программирования Java Blueprints». Документ для жюри: что сделано, как устроено, как проверить и чего в решении нет. Подробности — в [docs/](docs/README.md); приёмка по пунктам ТЗ — в [docs/13-acceptance.md](docs/13-acceptance.md).

## 1. Идея

Java-монолит (≈1000 строк) показывается одновременно как **код** и как **граф** (блок-схема каждого метода и граф структуры). Инструмент находит дефекты, оценивает сложность по Big O, предлагает исправления, выделяет методы, раскладывает монолит на классы — и после **каждого** изменения доказывает, что поведение программы не изменилось.

Путь пользователя: *Монолит → Граф → Диагноз → Улучшение → Тесты*. Весь он проходится в одном окне:

| Шаг | Что делает инструмент |
|---|---|
| Загрузка | файл, архив, вставка текста или встроенный пример; разбор, дерево проекта, метрики |
| Граф | блок-схема метода (переменная, условие Да/Нет, циклы-контейнеры, `try`, `switch`, вызовы); клик по блоку подсвечивает строки, курсор в коде выбирает блок |
| Правка | граф → код (палитра блоков, инспектор, перетаскивание, `Ctrl+D`, обернуть/развернуть) и код → граф (живой разбор за доли секунды); версии, undo/redo, история со сравнением |
| Диагноз | 34 правила (производительность, дефекты, сопровождаемость), оценка Big O с цепочкой вкладов, метрики; «Проверить» запускает программу на растущем вводе и показывает показатель роста `k` |
| Улучшение | 24 автопреобразования с предпросмотром и предусловиями, пакетная «Оптимизировать», «Выделить в метод», замена клонов, декомпозиция монолита на `Parser`/`Analyzer`/… |
| Тесты | сценарии (ручные, импорт, генератор по покрытию блоков), эталон, quality gate, трассировка («Дебаг»), отчёты JSON/Markdown/JUnit |

## 2. Архитектура

```
Браузер ── Next.js (React Flow + ELK, Monaco, shadcn/ui) ── /api/* ──▶ FastAPI
                                                                          │
                          app/ (HTTP, SQLite, очередь запусков, SSE) ─────┤
                          engine/ (без веб-зависимостей) ─────────────────┘
                              java/      tree-sitter-java: CST, символы, семантика, проект
                              graph/     блок-схемы, граф структуры, структурные ID, locate
                              edit/      операции над графом → точечные правки текста
                              analysis/  модель стоимости Big O, метрики, клоны, 34 правилаа
                              transform/ автоисправления, выделение метода, клоны, декомпозиция
                              runtime/   javac/java в песочнице, инструментирование (JbTrace)
                              verify/    нормализация вывода, сравнение, генератор сценариев, бенчмарк
```

Принципы, которые держат систему целой:

- **Источник истины — текст Java.** Граф всегда вычисляется из кода; операция над графом превращается в *точечную правку текста* по диапазону узла, поэтому форматирование и комментарии вне правки не меняются (инвариант I2: замена любого блока его же текстом не меняет ни байта).
- **Стабильные структурные идентификаторы** (`Main.java#Main.run(Scanner)/foreach[0]/if[1]`) переживают правки соседних блоков; интерфейс и backend говорят на одном языке идентификаторов.
- **Контракт API первичен.** Pydantic-схемы → OpenAPI → TypeScript-типы; CI проверяет, что сгенерированные типы актуальны.
- **Без LLM.** Диагностика, оптимизации, генерация сценариев и декомпозиция детерминированы: одинаковый вход даёт одинаковый результат, любое решение объяснимо.
- **Любое преобразование — это версия-кандидат.** Она становится HEAD, только если прошла gate.

## 3. Как гарантируется сохранение поведения

1. **Эталон (golden master).** Каждый сценарий (stdin + аргументы) запускается на исходной версии дважды: расхождение между прогонами помечает сценарий нестабильным или требует маски (время, хеши). Сравниваются нормализованные `stdout`, `stderr`, код выхода и тип/сообщение исключения.
2. **Quality gate** = синтаксис → компиляция `javac` → все сценарии против эталона → порог покрытия блоков (по умолчанию 60%). Зелёный gate продвигает кандидата в HEAD; красный — кандидат отклоняется, HEAD прежний, виден diff по сценариям.
3. **Исправления, меняющие поведение** (FIX-*, OPT-01) помечены `behavior_preserving = false`: их расхождения нужно подтвердить явно, а в пакетную оптимизацию они не входят.
4. **Негативный контроль:** тест меняет `+` на `-`, gate краснеет, diff и код выхода видны; откат возвращает зелёный.
5. **Проверка корпуса:** `scripts/verify_samples.py` прогоняет 6 примеров целиком через API (эталон → gate → анализ): все зелёные, покрытие 90–100%; `scripts/bug_bash.py` проводит весь корпус (48 проектов) через граф, анализ, предпросмотр каждого исправления, сборку, экспорт и повторную сборку `javac` вне инструмента — дефектов нет.

## 4. Поддержанный Java scope

Обязательный scope (язык и `java.lang`, консольный ввод-вывод, коллекции `java.util`, исключения) и бонусный (`record`, `enum`, дженерики, лямбды, Stream API) проверяются **38 фикстурами** `samples/scope/*` тестом `test_scope_matrix`: разбор без ошибок, все ожидаемые виды блоков в схеме, `javac` проходит, сценарии стабильны. Полная таблица «конструкция → граф → правка → анализ → тест» — [docs/04 § 9](docs/04-code-graph-model.md#9-покрытие-java-scope).

Вне рамок кейса (потоки, рефлексия, файлы, сеть, `java.time`): код сохраняется, компилируется и запускается; в графе такие места показываются блоком «Код» и не анализируются. Фикстуры — `samples/out-of-scope/`.

## 5. Диагностика и преобразования

| Группа | Состав |
|---|---|
| Производительность (13) | вложенный поиск, линейный поиск в цикле, поиск по ключу в методе, вызываемом из цикла, конкатенация строк в цикле, сортировка в цикле, инвариант в цикле, неподходящая коллекция, повторное вычисление, рекурсия без мемоизации, ручной подсчёт частот, вывод в цикле, лишняя работа в стриме, боксирование в цикле |
| Дефекты (11) | `==` для строк, пустой `catch`, незакрытый ресурс, деление на возможный ноль, разыменование `Map.get`, изменение неизменяемой коллекции, результат `String` отброшен, проглоченное исключение, изменение коллекции при обходе, `switch` без `default` и провалы, формат не соответствует аргументам |
| Сопровождаемость (10) | длинный метод, дублирование, вложенность, число параметров, монолит, магические значения, неиспользуемое, смешение ввода/расчёта/вывода, цикломатика, именование |
| Автоисправления | `OPT-01…09, 11, 12, 13`, `FIX-01/02/03/07/09/10`, `CLEAN-01/02/03`, `REF-02` (клоны → общий метод) — с предусловиями и отказом с причиной, если безопасность не доказана |
| Рефакторинги | `REF-01` выделение метода (параметры, результаты, `throws`, `record` для нескольких результатов), `REF-04` декомпозиция монолита (граф зависимостей, Louvain с фиксированным seed, роли, генерация «ядро хранит состояние») |

Оценка сложности — статическая модель стоимости с каталогом JDK и эвристиками; её уверенность помечена (`exact`/`heuristic`), а «Проверить» подтверждает её измеренным показателем роста.

## 7. Ограничения (честно)

- **GitHub Actions не запускались.** Backend и корпус проверены на Windows с JDK 17, а также в Docker (Linux, JDK 21): образы собираются, `docker compose up` поднимает приложение с готовым демо-проектом, весь pytest и E2E проходят. Не проверено только само выполнение CI на GitHub и запуск с нуля на другой машине (проверялась рабочая копия).
- **Время `demo-orders` после оптимизации не уменьшается.** Пакетная «Оптимизировать» (индекс для `findOrderById`, `OPT-02/03/09`; gate зелёный) снижает показатель роста `k` с 1,80 до 1,00, а число выполняемых блоков на N = 4000 — в 9,2×, но время программы остаётся прежним (≈ 0,9–1,0× при N = 8000): на размерах ввода, которые успевает пройти бенчмарк, время определяют запуск JVM и построчный ввод-вывод. Отчёт показывает оба показателя. Ускорение ≥ 2× по времени измеряется на примерах, где узкое место доминирует: линейный поиск, «найти или добавить», конкатенация (тест `test_optimize_reports_the_measured_speedup`: до ×9; `OPT-09` на подсчёте повторов: ×5,65).
- **Big O в глубоко слоёных монолитах завышена** (например `O(n^8)` у калькулятора выражений): один общий символ `n` перемножается по слоям вызовов; уверенность таких оценок помечается `heuristic`.
- **Не сделано:** `OPT-09` (`Map.merge` вместо ручного подсчёта) и `OPT-10` (буферизация вывода) — меняют структуры данных и поток вывода, остаются рекомендациями; `REF-03` (ранние возвраты); каталог типов JDK неполный (при неопределённости типа исправление не предлагается); эффекты и чистота методов вычисляются эвристически.
- **E2E проверены только в Edge и на dev-сервере.** Восемь сценариев Playwright (`frontend/e2e`, `pnpm e2e`) проходят локально в установленном Edge на живом backend; их запуск в CI на `docker compose` и в Chromium не проверялся.
- **Однопользовательский режим.** Один процесс backend, без аутентификации; пользовательский код выполняется в подпроцессах с лимитами времени, памяти и вывода, без сетевой изоляции (вход доверенный: монолиты присылают организаторы).

## 8. Запуск и проверка

```bash
docker compose up --build                    # http://localhost:3000, демо-проект «Demo: заказы» уже с эталоном и зелёным gate
cd backend && uv run pytest                  # тесты backend (нужен JDK; без него — pytest -m "not jdk and not slow")
cd frontend && pnpm test                     # тесты frontend
python scripts/verify_samples.py             # корпус через API → reports/verify_samples.md
python scripts/bug_bash.py                   # корпус целиком → reports/bug_bash.md
python scripts/perf_budget.py                # бюджеты → reports/perf_budget.md
python scripts/jdk_sweep.py                  # исходники JDK (нужен src.zip) → reports/jdk_sweep.md
make submit                                  # комплект сдачи → dist/
```

Сценарий демонстрации на 7 минут и ответы на вопросы жюри — [docs/12-demo-and-submission.md](docs/12-demo-and-submission.md).
